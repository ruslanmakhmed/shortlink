# Решения

## 1. Kustomize, а не Helm и не голые манифесты
Выбирал из трёх вариантов: голые манифесты, Kustomize, Helm. Менять между окружениями нужно только тег образа, а Helm-шаблоны ради одной переменной — лишний слой (Go-шаблоны, values, `helm lint`).
Kustomize встроен в `kubectl` (`apply -k`), манифесты остаются обычным YAML, а `configMapGenerator` собирает ConfigMap из настоящих файлов (`prometheus.yml`, `dashboard.json`) и добавляет хеш к имени, так что поды перезапускаются при правке конфигурации.
Тег образа при деплое подставляется временным overlay в `.build/deploy`. Если появятся два окружения с разными репликами и лимитами, это будут `overlays/dev` и `overlays/prod`.

## 2. PostgreSQL в StatefulSet, а не в Deployment с PVC
Deployment с одним PVC тоже сохраняет данные, но при `RollingUpdate` новый под стартует до остановки старого. На другом узле он зависнет в ожидании RWO-тома, а на том же узле (RWO ограничивает узел, не под) получатся два PostgreSQL на одном каталоге данных. Лечится `strategy: Recreate`, но об этом нужно помнить. К тому же имена подов у Deployment случайные.
У StatefulSet стабильное имя `postgres-0`, свой PVC `data-postgres-0` из `volumeClaimTemplates` и строгий порядок: новый под не создаётся, пока старый не удалён. Для базы это правильная семантика.
Бонус: `backup.sh` и RUNBOOK обращаются к `postgres-0` по имени.

## 3. База в кластере, а не отдельно
Внешней базы на стенде нет, а по условию всё поднимается с нуля из репозитория. База в кластере создаётся тем же `deploy`.
Цена: нет репликации, бэкапы — моя забота, том `local-path` живёт на одном узле k3d. В production я бы взял управляемую базу (см. CLOUD.md).

## 4. Prometheus собирает метрики с каждого пода, а не через Service
Цель `shortlink:8080` из примера задания попадает в Service, то есть каждый раз в случайный под. У каждого пода свои счетчики, поэтому в одном временном ряду значения скакали бы между подами, а `rate()` видел бы ложные сбросы.
`kubernetes_sd_configs` с ролью `pod` делает каждый под отдельной целью с меткой `pod`, и `sum(rate(...))` складывает их честно. За это нужны RBAC (ServiceAccount + ClusterRole на чтение подов) и доступ к `nodes/proxy` для памяти из cAdvisor.

## 5. Секреты создаются при деплое, а не хранятся в Git
Варианты: Secret в Git (нельзя по условию), Sealed Secrets или SOPS (новые инструменты, вне рамок проекта), генерация при деплое.
`run-stage.sh deploy` создаёт Secret со случайным паролем, только если его ещё нет, поэтому повторный деплой не рассинхронизирует пароль с уже инициализированной базой. В Compose пароль передаётся Docker secret'ом из файла (`POSTGRES_PASSWORD_FILE`, `DB_PASSWORD_FILE`): его нет ни в compose-файле, ни в `docker inspect`. В Ansible секрет — хеш пароля для `/metrics` в Ansible Vault.

## 6. cron, а не systemd-таймер, для healthcheck.sh
Таймер даёт журнал в `journalctl`, зависимости и `Persistent=`, но это два unit-файла, шаблоны и `daemon-reload`. cron — одна идемпотентная задача модулем `ansible.builtin.cron`.
Проверке раз в несколько минут пропущенные запуски не важны, а вывод и так уходит в журнал через `logger -t shortlink-healthcheck`. Поэтому cron.

## 7. Деплой только по тегу vX.Y.Z; lint без доступа к кластеру
Каждый коммит проходит lint, build и push, но в кластер попадает только осознанно выпущенная версия. Её git-тег совпадает с тегом образа, поэтому по версии всегда понятно, что запущено и на что откатываться. `latest` не используется нигде.
Стадия lint проверяет манифесты через `kubectl kustomize | kubeconform -strict`: `kubectl apply --dry-run=client` всё равно требует API-сервер для discovery, а kubeconform сверяет с OpenAPI-схемами Kubernetes без кластера, поэтому одинаково работает на стенде и в CI.

## 8. Python на стандартной библиотеке, образ slim, а не alpine
HTTP-сервер и метрики написаны на стандартной библиотеке, единственная зависимость — `psycopg2-binary`. Под musl (alpine) у неё нет стабильных колёс, пришлось бы ставить компилятор. Двухстадийная сборка оставляет в итоговом образе только venv и `app.py`, без pip-кэша.
Процесс в контейнере — PID 1, поэтому в приложении есть обработчик SIGTERM. Без него сигнал игнорируется, и `docker stop` или удаление пода ждали бы таймаут до SIGKILL.
